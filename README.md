# Flower Classifier API

An end-to-end deep learning project: a convolutional neural network (CNN) that
classifies flower photos into 5 species, served behind a production-style
**FastAPI** inference endpoint. Upload a photo, get a prediction with
confidence scores.

**Classes:** daisy · dandelion · rose · sunflower · tulip

![Demo prediction](docs/demo_prediction.png)

---

## Why this project is structured the way it is (interview notes)

Every design decision here answers a question that comes up in ML interviews:

| Decision | Interview question it answers |
|---|---|
| Model loaded **once at startup** (singleton) into `app.state` | "How do you avoid reloading weights on every request?" |
| `train.py` is separate from the API | "How do you separate the training and serving pipelines?" |
| Input **validation** (MIME type, size, decodability) with proper HTTP codes | "How does your API fail gracefully on bad input?" |
| Pydantic **response schema** | "How do you version and document your API contract?" |
| Preprocessing defined **once** in `app/model.py` and reused | "How do you prevent train/serve skew?" |
| Tests with `TestClient` and an in-memory image | "How do you test an ML service without a running server?" |
| Augmentation on train split **only** | "What is data leakage and where does it hide?" |
| Artifacts saved as `state_dict` + `config.json` | "How do you version models and keep inference reproducible?" |

### Known limitations (say these out loud in an interview — they score points)

- The training set is tiny (~70 images scraped from the web, some with stock
  photo watermarks = label noise). Validation accuracy is **~79%** on 14
  images, so treat the number as indicative, not definitive.
- The obvious upgrade path is **transfer learning** (freeze a ResNet18 /
  MobileNetV3 pretrained on ImageNet, fine-tune the head). With ~70 images,
  feature extraction on frozen pretrained layers would likely jump accuracy
  to the high 90s — a great follow-up exercise.
- No batching/queueing — fine for a demo; in production you'd add async
  workers or a model server (TorchServe, Triton).

## Project structure

```
flower-classifier/
├── app/
│   ├── __init__.py
│   ├── main.py            # FastAPI app: routes, validation, lifespan
│   ├── model.py           # CNN architecture + FlowerPredictor (load & inference)
│   └── static/
│       └── index.html     # Browser UI: drag & drop a photo, see prediction
├── model/
│   ├── flower_cnn.pth     # trained weights (~2 MB)
│   └── config.json        # classes, image size, normalization (train/serve contract)
├── tests/
│   └── test_api.py        # API tests with FastAPI TestClient
├── train.py               # full training pipeline (run me to retrain)
├── requirements.txt
└── docs/
    ├── demo_prediction.png
    └── training_report.png
```

## Quickstart

```bash
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Then either:

- **Browser UI:** open http://127.0.0.1:8000/ and drag a flower photo onto the page
- **curl:**
  ```bash
  curl -X POST "http://127.0.0.1:8000/predict" \
       -H "accept: application/json" \
       -F "file=@/path/to/flower.jpg"
  ```
- **Interactive API docs:** http://127.0.0.1:8000/docs (Swagger UI, auto-generated by FastAPI)

Example response:

```json
{
  "class_name": "dandelion",
  "confidence": 0.65,
  "probabilities": {
    "daisy": 0.02,
    "dandelion": 0.65,
    "rose": 0.0,
    "sunflower": 0.33,
    "tulip": 0.0
  }
}
```

### API reference

| Endpoint | Method | Description |
|---|---|---|
| `/` | GET | Upload UI |
| `/predict` | POST | Upload an image (`multipart/form-data`, field `file`). Returns JSON prediction |
| `/health` | GET | Liveness probe — model loaded or not |
| `/model-info` | GET | Classes, input size, normalization from `config.json` |
| `/docs` | GET | Auto-generated Swagger UI |

Error codes: `415` wrong file type · `413` file too large (10 MB) · `400` undecodable image.

## Retraining

Put photos in `data/flowers/<class_name>/` and run:

```bash
python train.py --epochs 40 --out model/
```

The script reproduces the shipped model: stratified 80/20 split, augmentation
(RandomResizedCrop, flip, rotation, color jitter — train split only), a compact
VGG-style CNN with BatchNorm + dropout, Adam + cosine LR, and **early stopping**
on validation accuracy (best checkpoint is kept, not the last).
